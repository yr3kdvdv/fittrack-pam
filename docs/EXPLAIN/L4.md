# L4 — State management и Repository: объяснение

Перед защитой студент должен сам пройти каждый файл ниже и уметь объяснить
его своими словами — код, который не может быть объяснён, не засчитывается.

## Слои

```
экраны / widgets ── watch в build, read в callback-ах, Consumer для badge
        ▼
models: WorkoutsModel · ExercisesModel · ProfileModel   (ChangeNotifier)
        │  Future<Result<T>>; repository пришёл в конструктор как интерфейс
        ▼
data:  WorkoutRepository (CRUD) · ExerciseRepository · ProfileRepository
        ▲  implements
data:  MockWorkoutRepository · MockExerciseRepository · MockProfileRepository
       + MockNetwork (800 мс + один флаг аварии) + mock_data.dart (seed)
```

- **Экраны** не знают источника данных: они видят только модели.
- **Модели** хранят разделяемое состояние и триаду loading / data / error,
  мутируют данные только через repository и извещают подписчиков.
- **Интерфейсы** говорят, ЧТО можно просить; каждый метод на L5 станет
  одним REST-запросом.
- **Mock** — сегодняшняя реализация в памяти, с задержкой и аварией.
- **main.dart** — корень композиции: единственное место, где выбирается mock.

## Ключевые решения и альтернативы

- **String id** остался с L1–L3 (`ws-13`, `ex-01`), адреса не изменились.
  Новые id выдаёт mock: `ws-1000`, `ws-1001`… (на L5 — сервер).
- **Три mock-класса, один MockNetwork.** У сессий и упражнений одинаковые
  имена методов `fetchAll/fetchById`, один класс их не вместит. Общий
  `MockNetwork` — одна задержка и один флаг аварии на все хранилища, поэтому
  выключатель в профиле роняет все экраны сразу.
- **Каталог и профиль только читаются** — пишущей формы упражнений в T2 нет.
  Группы мышц фильтра выводятся из загруженного каталога, техника грузится
  через `fetchTechnique` по id, профиль — через `ProfileRepository`.
- **Статистика вычисляется** (`WorkoutStats.fromSessions`) из актуального
  списка, а не хранится: после мутации цифры не могут разойтись с дневником.
  Подпись «За всё время · недель с тренировками: N»: seed заканчивается в
  октябре, окно «последние 6 недель от сегодня» было бы пустым.
- **Эфемерное состояние осталось в State:** текст поиска и выбранная группа
  мышц, контроллеры и выбранные упражнения формы, флаг `_busy`, bool
  выключателя аварии. Это не нужно другим экранам.
- **SafeNotifier** — mixin: ответ «сети» может прийти после `dispose` модели;
  без защиты `notifyListeners` бросил бы ошибку.
- **Устаревший ответ загрузки.** Если пока `fetchAll` в пути успела пройти
  мутация, ответ мог быть собран до неё; модель спрашивает список ещё раз,
  чтобы не откатить добавленную запись.
- **Форма заполняется один раз** (`_fillOnce`): последующие извещения модели
  и перезагрузки не стирают ввод. После сохранения — `pop`; если форму
  открыли прямым адресом и стека нет — `go('/workouts')`.
- **confirmDismiss ждёт ответа хранилища** и возвращает true только при
  успехе: при отмене, null или ошибке карточка возвращается на место.

## Поток демонстрации (защита)

1. Запуск → вход → каталог: spinner ~0,8 с, затем список.
2. Детали упражнения; поиск «жим» + фильтр «Грудь».
3. Дневник: badge = 13. «Новая тренировка» → валидный submit → список
   вырос, badge 14, статистика и профиль показывают 14 без перезагрузки.
4. Свайп или кнопка удаления в форме → диалог → «Удалить» → запись исчезла
   отовсюду, badge уменьшился.
5. Профиль → «Симулировать сбой сети» → «Обновить» → spinner → ошибка с
   «Повторить» (без crash) → выключить → «Повторить» → данные. Submit формы при
   аварии → SnackBar с ошибкой, поля остаются.
6. Перезапуск приложения → снова 13 тренировок: персистентности на L4 нет.

## Вопросы преподавателя и ответы

- **watch/read — где что?** `context.watch` в build: экран подписывается и
  перестраивается при извещении. `context.read` в callback-ах: одно действие
  без подписки. `read` в build молчит — badge замирает (тихая ошибка);
  `watch` в callback падает с исключением сразу (громкая).
- **Забытый `notifyListeners()`?** Данные в модели верные, но уже видимые
  экраны не перестраиваются; экраны, построенные позже, читают правильный
  список. Поэтому баг «иногда работает» и его трудно поймать.
- **Зачем `List.unmodifiable`?** Иначе экран мог бы вызвать
  `model.sessions.add(...)` в обход `notifyListeners` и рассинхронизировать
  остальные экраны. Теперь такая попытка бросает `UnsupportedError`.
  `exerciseIds` внутри сессии тоже неизменяемый.
- **Почему `Future<Result<T>>`, а не исключения?** Ожидаемый отказ — значение.
  `switch` по `sealed Result` исчерпывающий: компилятор не даст забыть ветку
  `Err`. `delete` возвращает `Result<void>` — как HTTP 204 без тела.
- **Зачем `Future.delayed`?** Без задержки состояние «грузится» длится 0 мс —
  его нельзя увидеть и показать, spinner становится мёртвым кодом.
- **Почему repository в конструктор?** Модель зависит от интерфейса и не
  знает, mock это или http. Тесты подставляют хранилище без задержки, а на L5
  меняется только `main.dart`.
- **Что трогаем на L5?** Новые http-реализации трёх интерфейсов и строки в
  `main.dart`. Экраны и модели не меняются; выключатель аварии в профиле,
  `MockNetwork`, mock repositories и `mock_data.dart` удаляются.
- **Неизвестный или удалённый id?** Пока модель грузит — spinner; ошибка —
  ErrorView с retry; загружено, но id нет — «не найдено» с кнопкой возврата,
  а не вечный spinner.
- **Почему `mounted` после `await`?** Пока запрос летит, пользователь может
  уйти с экрана; обращение к context мёртвого экрана — ошибка.
- **Почему `ValueKey(session.id)`?** Идентичность из данных: при удалении
  Flutter сопоставляет карточки по id, а не по позиции, и не переносит
  состояние одной карточки на соседнюю. `UniqueKey` менялся бы каждый build.

## Проверки

Из `app`: `dart format --output=none --set-exit-if-changed lib test`,
`flutter analyze`, `flutter test`. Тесты покрывают модели (коллекции только
для чтения, извещения, ошибки без изменений, устаревший ответ, dispose),
каждый метод mock (задержка 800 мс, авария, неизвестный id, уникальные id,
копии), триаду всех экранов, сохранение/редактирование/удаление/отмену,
двойное нажатие, выключатель аварии и регрессии L3 (валидация, вкладки,
прямые адреса, выход, узкий экран).
